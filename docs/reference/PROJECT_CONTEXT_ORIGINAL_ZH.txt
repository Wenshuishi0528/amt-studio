AI歌曲识谱软件——需求、资源、技术判断与待决策事项
整理日期：2026-07-23

说明：
这是一份完整背景资料，准备发送给网页版GPT继续讨论。项目目前仍处于可行性分析和路线选择阶段，尚未正式开始开发或训练。


一、项目动机

1. 我很早以前就想做一个AI歌曲识谱软件。
2. 我过去只能使用网上的付费会员服务，把歌曲转换成MIDI或乐谱。
3. 我测试过很多现有软件，但复杂歌曲的识别准确率普遍不理想，尤其容易出现：
   - 主旋律找错。
   - 音高或八度错误。
   - 颤音、滑音被拆成大量错误音符。
   - 节拍、小节和音符时值错误。
   - 人声、和声、伴奏互相串音。
   - 生成的MIDI大致能听，但谱面很难直接使用。
4. 我希望最终拥有一个不依赖会员、可以本地使用、能够持续改进的软件。
5. 我目前人在美国，并且还有University of Washington的Hyak超算使用权限，因此现在可能是开展这个项目的较好时间窗口。


二、最初提出的核心需求

最低必须达到的第一项功能：

导入或上传一首完整歌曲，AI识别歌曲的主旋律，并生成可以试听、编辑和导出的音符或乐谱。

后续希望逐步增加：

1. 识别低音声部。
2. 识别鼓和打击乐，例如底鼓、军鼓、踩镲等。
3. 识别和弦。
4. 识别钢琴、吉他及其他伴奏。
5. 最终尝试生成多乐器总谱。

第一版较合理的“主旋律”定义：

当歌曲中有清晰主唱时，默认把主唱演唱的旋律定义为主旋律。纯音乐、前奏、间奏、和声及多个领奏乐器同时存在的情况，后续再增加候选声部选择功能。


三、对产品能力边界的认识

目前技术上可以较现实地实现：

1. 清晰主唱的流行、摇滚、民谣等录音室歌曲。
2. 提取单条主唱旋律。
3. 输出可编辑的MIDI和MusicXML。
4. 生成一份保留真实演唱时值、滑音和颤音的“演奏版”。
5. 生成一份经过节拍、小节和音符时值整理的“谱面版”。
6. 对低置信度音符进行颜色提示，并允许用户快速修改。

目前不应在第一版承诺：

1. 任意歌曲都能准确识别。
2. 自动生成出版级完整总谱。
3. 准确识别密集多声部钢琴或吉他和弦。
4. 自动理解所有前奏、间奏、和声、合唱、说唱及自由速度音乐。
5. 一次识别就完全不需要人工校对。

合理的产品定位应是：

“生成明显更准确、只需检查少量低置信位置的转谱初稿，显著减少人工扒谱时间。”


四、为什么现有软件准确率低

完整歌曲识谱不是一个单独任务，而是多个任务的组合：

1. 从混音中分离人声、鼓、低音和其他伴奏。
2. 判断哪个声部是主旋律。
3. 从颤音、滑音、气声和咬字中估计连续音高。
4. 判断一个新音符从哪里开始、在哪里结束。
5. 识别速度、拍点、强拍、拍号和小节。
6. 把真实演奏时间整理成四分音符、八分音符、附点和三连音。
7. 判断调号、升降号、连音线和休止符。
8. 将音符事件转换成真正可读的乐谱。

因此“音高识别正确”并不等于“谱面正确”。分轨产生的串音和伪影也可能制造假音符或吞掉真音符。


五、建议的系统技术路线

不建议只连接一个模型直接输出结果，应采用多阶段、双路径系统：

路径A：保留原混音直接识别，避免分轨过程把弱音删除。

路径B：先分离出人声或候选主奏声部，再运行专用音高和音符模型。

然后：

1. 对齐两路的时间和音高结果。
2. 两路一致的音符标为高置信度。
3. 两路不一致的位置进入待检查。
4. 使用节拍、调性、合理音域和旋律连续性纠正八度错误与极短杂音。
5. 利用重复的主歌、副歌进行多次投票。
6. 同时保留未量化的演奏结果和经过整理的谱面结果。
7. 生成MIDI、MusicXML、PDF，以及可选的简谱。

可能使用的现有组件：

1. GAME
   - 专门用于歌声到MIDI/乐谱的识别。
   - 官方默认训练配置约5000万参数，约消耗20GB显存。
   - 适合识别人声音符边界和音高。
   - 代码为MIT许可。

2. Basic Pitch
   - 轻量、支持CoreML、ONNX等部署方式。
   - 适合分离后的单一乐器或声部。
   - 官方明确说明它最适合一次识别一种乐器，不适合直接承担复杂整曲多乐器识别。
   - Apache 2.0许可。

3. Demucs或更新的分轨模型
   - 用于分离vocals、drums、bass、other。
   - Demucs代码为MIT，但原仓库已归档。
   - 正式商业发布前仍需要检查具体模型权重和训练数据许可。

4. Beat This!
   - 用于节拍和强拍识别。
   - 代码与已发布模型权重为MIT。

5. MuScriptor
   - 2026年发布的多乐器整曲转录模型。
   - 可以作为研究阶段的多乐器上限参考。
   - 作者测试集上起音F1约60.4%，严格的音高、时间和乐器全部正确的Multi F1约47.8%，说明整曲多乐器转谱仍未彻底解决。
   - 代码MIT，但官方权重为CC BY-NC，不能直接用于收费商业产品。


六、目前拥有的硬件和计算资源

本地设备：

1. MacBook M4
   - 适合SwiftUI界面、AVFoundation音频播放、CoreML转换、最终macOS本地部署和打包。

2. Windows台式机
   - NVIDIA RTX 4070 Super，12GB显存。
   - 适合日常模型安装、单首歌曲调试、短实验和部分小模型微调。
   - CUDA生态兼容性通常比Mac的MPS更好。

University of Washington Hyak Klone：

账户拥有STF优先资源，而不只是临时Checkpoint资源。

hyakalloc观测到的资源：

1. stf / gpu-l40
   - 总计8张GPU。
   - 观测时已使用6张，账户资源中有2张空闲。
   - L40单卡48GB显存。

2. stf / gpu-l40s
   - 总计10张GPU。
   - 观测时10张全部使用中。
   - L40S单卡48GB显存。

3. CPU资源
   - compute、compute-hugemem、cpu-g2及cpu-g2-mem2x。
   - 可用于音频解码、切片、特征提取和数据预处理。

4. Checkpoint资源
   - 观测时全集群约有1195个CPU和196张GPU处于空闲状态。
   - 可以临时申请A100、A40、L40、L40S甚至H200等空闲GPU，但可用性和连续性不保证。

推荐设备分工：

1. Hyak L40/L40S：主要AI实验、批量评测、参数搜索和模型微调。
2. Windows 4070S：快速交互调试和单首歌曲实验。
3. MacBook M4：最终软件界面、CoreML/ONNX适配、本地运行与打包。


七、Hyak使用注意事项

1. 不能在klone登录节点直接运行模型或重型计算。
2. 应通过Slurm的salloc或sbatch申请计算节点。
3. 建议使用Apptainer固定PyTorch、CUDA和模型依赖，确保实验可复现。
4. 推荐先申请一张L40：

salloc \
  --account=stf \
  --partition=gpu-l40 \
  --nodes=1 \
  --gpus=1 \
  --cpus-per-task=8 \
  --mem=64G \
  --time=02:00:00

5. 分配成功后使用hostname和nvidia-smi确认计算节点与GPU。
6. /gscratch/scrubbed中的数据不是长期存储，未访问文件可能自动删除。
7. Scrubbed默认权限可能较开放，歌曲文件需要主动设置严格权限。
8. 重要数据、模型权重和评测结果必须另外备份。
9. 如果未来商业化，应在使用UW/STF资源训练商业产品前确认UW、PI、课题组和相关资源使用规定。


八、是否需要从头训练模型

第一版不需要从头训练整套系统。

建议分为三个层次：

第一层：不训练

1. 使用现有预训练模型。
2. 自己完成数据管线、多模型融合、置信度、节奏量化、MusicXML生成和编辑器。
3. 先验证能否超过现有付费工具。

第二层：小规模微调

针对持续出现的具体错误微调小模块，例如：

1. 音符边界。
2. 主旋律声部选择。
3. 八度纠错。
4. 置信度预测。
5. 中文演唱咬字、滑音或三连音。

第三层：从随机权重训练自己的主旋律模型

可以复用现有模型架构和训练代码，但模型权重从随机值开始训练。

建议只从头训练：

“已经分离好的人声 → 音高、起音、收音、是否有人声”

不建议一开始从头训练：

1. 分轨模型。
2. 节拍模型。
3. 多乐器总谱模型。
4. 整套端到端万能模型。


九、从头训练的可行性和时间判断

一个星期可以完成：

1. 在Hyak上建立可复现训练环境。
2. 整理一个小型公开研究数据集。
3. 从随机权重训练一个小型人声主旋律模型。
4. 生成训练曲线和验证指标。
5. 与Basic Pitch或GAME预训练模型进行比较。
6. 输出若干成功、失败的MIDI样例。
7. 做一个命令行或简单网页演示。

一个星期不能合理完成：

1. 适用于任意歌曲的高准确率模型。
2. 出版级完整乐谱。
3. 完整多乐器识别。
4. 同时完成模型、Mac正式应用、打包和充分测试。
5. 超过经过大量数据训练的商业模型。

大致周期判断：

1. 清晰独唱或单乐器到音高曲线：
   - 一周可以完成实验版。

2. 分离后的人声到主旋律MIDI：
   - 一周可完成研究基线。
   - 约4至8周进行改进更现实。

3. 完整歌曲到可靠主唱旋律：
   - 约2至4个月更现实。

4. 完整歌曲到全部乐器总谱：
   - 通常需要6至12个月以上，可能需要团队、大量有权利的数据和更多GPU资源。

参考研究规模：

Mel-RoFormer相关研究中的人声分离预训练，曾使用8张A100 80GB训练约40天；更大数据版本使用16张A100训练约93天。这说明高水平整套模型无法在一周内从零复现。


十、第一周如果坚持从头训练，可执行的目标

建议将第一周定义为：

“在Hyak上从随机权重训练一个人声主旋律转写模型，并证明它在一个小型盲测集上学会了音高和音符边界。”

建议日程：

第1天：建立Apptainer、PyTorch和CUDA环境。
第2天：准备拥有研究使用权的音频—音符数据。
第3天：完成预处理、训练集、验证集和测试集划分。
第4至5天：在一张L40上训练小模型。
第6天：与Basic Pitch、GAME等基线比较。
第7天：生成评测报告、MIDI样例和简单演示。

第一周合理交付物：

1. 自训练模型checkpoint。
2. 训练配置和可复现实验脚本。
3. 训练曲线。
4. 验证和盲测指标。
5. 成功与失败案例。
6. 与预训练模型的对照实验。
7. 简单可运行演示。


十一、准确率验证与停损条件

不应先投入大量时间制作漂亮界面。第一步应建立准确率基准。

建议准备：

1. 20至30段最初技术验证片段。
2. 后续扩展到50至100段，每段30至60秒。
3. 包含现有付费软件识别最差的歌曲。
4. 覆盖男女声、不同音域、和声、混响、现场、说唱、滑音、三连音和转调等情况。
5. 训练、验证和测试必须按歌手或歌曲分开，避免数据泄漏。

需要评估：

1. 音高和起音正确率。
2. 带收音时间的音符F1。
3. 八度错误率。
4. 主旋律声部选择正确率。
5. 节拍和小节对齐。
6. 高置信度音符的真实准确率。
7. 每分钟需要人工修改的音符数量。
8. 修完一分钟歌曲所需的时间。

建议继续做正式应用的条件：

1. 在目标歌曲上明显优于当前付费工具。
2. 人工修谱时间至少减少一半。
3. 低置信度提示确实能定位大部分错误。

如果不能达到这些条件，应暂停制作正式UI，先解决模型、数据或产品范围问题。


十二、软件第一版的建议界面

建议做成一个独立、本地、中文优先、单窗口Mac应用：

1. 拖入MP3、WAV或M4A。
2. 默认选择“识别主唱旋律”。
3. 显示“分离人声、识别音符、整理节拍、生成乐谱”的进度。
4. 上方显示五线谱或简谱。
5. 下方显示波形或钢琴卷帘。
6. 同步试听：
   - 原曲。
   - 分离人声。
   - 钢琴合成的识别结果。
7. 低置信度音符使用黄色或红色。
8. 支持升降音、移动、拆分、合并、延长和删除。
9. 导出MIDI、MusicXML、PDF和可选简谱。
10. 默认本地处理，不上传用户歌曲。


十三、简历价值

如果只运行Basic Pitch并套一个界面，简历价值较弱。

如果完成以下内容，项目会有较强的AI/ML简历价值：

1. 建立有明确划分的评测集。
2. 比较多个模型并进行消融实验。
3. 自己设计双路径融合和置信度系统。
4. 在Hyak上使用Slurm和Apptainer完成可复现实验。
5. 微调或从随机权重训练一个主旋律核心模型。
6. 使用真实指标证明相对基线的改进。
7. 将模型部署为本地macOS软件。
8. 输出技术报告、开源代码、演示视频或论文。

适合对应的职位：

1. AI/ML Engineer。
2. Applied Scientist。
3. Research Engineer。
4. Audio ML或Music Technology。
5. Software Engineer。
6. HPC或科学计算相关职位。

简历描述示例：

Developed an automatic music transcription system combining vocal source separation, pitch/onset detection, beat tracking, confidence-aware model fusion, and MusicXML generation. Built reproducible PyTorch experiments on UW Hyak using Slurm and Apptainer, then deployed the optimized inference pipeline as a local macOS application.

如果最终获得真实数据，可以增加：

Improved note-onset F1 by X points over the baseline and reduced manual score-correction time by Y%.

其中X和Y必须来自真实盲测，不能提前编写。


十四、目前的总体判断

这个项目技术上可行，但要严格控制第一版范围。

如果目的只是偶尔识别少量歌曲、节省会员费，购买现有服务的总成本可能低于开发成本。

但这个项目仍然值得考虑，因为：

1. 这是一个长期真实需求，不是临时想法。
2. 我已经体验过现有产品，知道具体痛点。
3. 现在同时拥有Mac M4、4070S和Hyak L40/L40S资源。
4. 可以形成兼具研究、HPC、机器学习和完整产品部署的简历项目。
5. 即使不商业化，也可以成为长期本地使用的个人工具。

推荐策略：

先把它作为“有明确停损条件的音频AI研究与产品原型”来做，而不是立即承担完整商业产品。


十五、需要继续确认的关键问题

1. 第一版是否确定只支持“有清晰主唱的歌曲”？
2. 主旋律是否默认定义为主唱旋律？
3. 第一版输出优先级：
   - 五线谱。
   - 简谱。
   - MIDI。
   - MusicXML。
   - PDF。
4. 最终是否优先做完全本地的Mac版本？
5. 项目是个人研究、简历项目，还是以后可能商业化？
6. 每周实际可以投入多少时间？
7. 是否拥有可以合法用于训练和评测的音频—乐谱数据？
8. 是否愿意先做一周训练实验，而不是直接做完整软件？
9. 是否希望训练自己的主旋律模型，还是优先追求产品准确率？
